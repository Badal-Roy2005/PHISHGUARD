# M9.1 — Authenticated Scan Persistence Fix

**Date:** 2026-11-09
**Scope:** Fix defect **D1** from
[`M9-functional-integration-audit.md`](./M9-functional-integration-audit.md) and
re-verify the authenticated scan → persistence → detail loop.
**Status labels used:** Implemented / Tested / Integrated / Verified against the
hosted Supabase project. **Not deployed** — no commit, no push, no production
deployment was performed.

---

## 1. Root cause

`apps/web/app/api/scan/route.ts` called:

```ts
callAnalysis(body, "", requestId);
```

`apps/web/lib/analysis.ts` omits `X-Authenticated-User-Id` when the id is falsy:

```ts
if (userId) {
  headers["X-Authenticated-User-Id"] = userId;
}
```

`services/analysis/app/main.py` persists only when that header is present, and
`persistence.py::persist_scan` requires a valid UUID. So every authenticated web
scan returned **200** while writing **zero** rows. The route never read the
Supabase session at all; it also used an ad-hoc `isScanRequest` duck-type check
instead of the contract validator.

A correct implementation already existed but was dead code:
`apps/web/lib/api/scan.ts::createScanResponse()` called `getUser()`, validated
with `validateScanRequest`, and passed `user.id` — but rejected anonymous callers
with 401 and was not imported anywhere.

## 3. Exact implementation

### 3.1 Verified identity comes only from the session

```ts
async function getVerifiedUser(): Promise<{ user: { id: string } | null }> {
  const supabase = await createClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();
  return { user: user ? { id: user.id } : null };
}
```

`createClient()` is the existing `@supabase/ssr` server client
(`apps/web/lib/supabase/server.ts`). `supabase.auth.getUser()` validates the
session token with Supabase Auth on the server; it does not decode and trust a
JWT, and it does not read anything from the request body.

The route then wires the existing helper:

```ts
const result = await createScanResponse({
  body,
  getUser: getVerifiedUser,
  analyze: (payload, userId) => callAnalysis(payload, userId, requestId),
});
return NextResponse.json(result.body, { status: result.status });
```

`MAX_BODY_BYTES` / 413, invalid-JSON 400, and `X-Request-ID` forwarding are
preserved.

### 3.2 Anonymous scans work and never persist

```ts
// Scanning is allowed anonymously; only a verified session supplies an owner.
// A null user id means the analysis service must not persist the scan.
return await analyze(parsed.value, user?.id ?? null);
```

`callAnalysis` omits `X-Authenticated-User-Id` for `null`, and the analysis
service does not persist without it. No change was made to the analysis service.

### 3.3 Client-supplied identity is never trusted

- **Body:** `validateScanRequest` rejects unknown fields, so `{..., user_id}` or
  `{..., userId}` returns `400 invalid_request` before analysis runs.
- **Headers:** the route forwards only `X-Request-ID`; it constructs the
  `X-Authenticated-User-Id` header itself from the verified session, so an
  inbound `X-Authenticated-User-Id` from the browser is discarded.
- **Session cookies** are the only credential path, and they are verified
  server-side.

### 3.4 Safe failure modes

| Situation | Behavior |
| --- | --- |
| No session | 200, anonymous, no persistence |
| Expired / invalid session | `getUser()` yields no user → anonymous, 200, no persistence |
| Auth backend throws | 503 `upstream_unavailable`; scan is **not** run |
| Missing/invalid body | 400 `invalid_request`; scan is **not** run |
| Analysis service down | 503 (unchanged) |

### 3.5 Security boundaries preserved

- RLS policies and migrations: **unchanged**.
- Service-role key: still referenced **only** server-side for testing/persistence
  plumbing outside `apps/web`; no client-side service-role access was added.
- Service-token authentication to `/internal/analyze`: **unchanged**
  (`require_service_token`).
- `/api/scan` was deliberately made public so anonymous scanning is reachable.
  This does **not** grant identity: ownership is derived from the verified
  session inside the handler, and `/account` + `/api/scans*` remain protected.

Creates two disposable Supabase users (Admin API), signs in via `@supabase/ssr`,
and asserts against real rows through PostgREST (service key, server-side only):

1. anonymous `POST /api/scan` → 200 and **zero** new rows;
2. authenticated A → 200 and **exactly one** row owned by A;
3. `GET /api/scans/<id>` → 200 as A, **404** as B; detail page 200 as A, 404 as B;
4. forged body `user_id` → 400 and B gains **zero** rows;
5. forged `X-Authenticated-User-Id` → row belongs to verified A, B gains zero;
   forged header while anonymous persists nothing;
6. invalid/expired session → 200/401/503 and **zero** new rows.

It deletes its scans and users in a `finally` block and is skipped unless
`M9_INTEGRATION=1`, so `pnpm test` stays hermetic.
